# Architecture

`craken` is a small Go CLI that executes the server-owned client catalog. It keeps machine-local behavior in the binary: profile storage, device-code browser login polling, request formatting, file upload/download, polling loops, and WebSocket transport.

The Worker remains the source of truth for product behavior. Product shortcuts such as `workspace list`, `channel send`, and `wiki save` are discovered from the server-owned `/api/client` catalog and executed from the catalog's command plan. Those plans describe path bindings, lookup resolvers, multipart fields, download behavior, polling termination, WebSocket protocols, and compact table output. The binary keeps only local bootstrap and generic transport primitives. `commands`, `do`, and raw HTTP commands use the same catalog route contract as the ergonomic shortcuts.

Generic `do` also accepts an additive route-level `execution` plan for multipart uploads, byte downloads, and WebSocket streams. It fetches the catalog once and uses the same transport executor as product shortcuts; operation ids and protocols stay server-owned. Path flags and positional arguments retain catalog name resolution. Older routes without `execution` keep the existing JSON/REST behavior. Multipart plans may set `fileOptional` to support public-URL-only forms; otherwise the advertised file option remains required. Uploads use the selected route's HTTP method. `--output` writes downloads to disk, and WebSocket plans retain the existing NDJSON, cancellation, checkpoint, and recovery behavior.

Wiki saves follow the service's optimistic concurrency contract. Creating a missing page can omit `--base-version`; updating an existing page should read the page first, edit against the returned `latestVersionNumber`, and pass that number as `--base-version`. A stale base version returns the server's 409 conflict payload so scripts can re-read, merge, and retry.

Local bootstrap command help is rendered without reading profiles or contacting the server. Resource-level product help is derived from the live catalog. Catalog help fetches are bounded to ten seconds and use an explicitly labeled minimal local fallback on network/schema failures; fallback JSON omits unconfirmed auth and never reuses prior session guidance. Profile/server selection is shared by HTTP clients, login, and `auth whoami`, and JSON help carries this local connection metadata alongside server-owned guidance.

Ordinary text help omits profile/server metadata; `auth whoami`, verbose help, JSON guidance, and connection-failure diagnostics expose it. The compact overview begins with the server summary and reserves its title for the verbose reference.

The default help fetches `/api/client` once and renders a compact, state-aware overview: the product summary, a one-line auth status, the server-recommended next steps, and a grouped command summary, with pointers to the fuller views. The catalog is derived from the selected bearer session, so the same request returns different guidance before and after login; the CLI only lays out what the Worker sends. Two server-owned fields drive the state-specific parts — `auth` (status `anonymous`/`user`/`agent`, identity, and for delegated agents an agent block) and `nextSteps` (an ordered `{title, command, description}` list whose commands are ready to run, with the known workspace id pre-substituted for agents). Both are additive (schema version unchanged); when an older server omits them the CLI falls back to a minimal hint and skips the status line. `craken help --verbose` renders the full reference (every server help section, the local bootstrap commands and flags, every command with descriptions and examples, and every operation route); `craken help --format json` emits the `auth`/`nextSteps` guidance as JSON for AI agents. Operation help such as `craken channel messages --help` focuses on the matching server command when it is present, then derives shortcut options from path/query/body/multipart execution bindings and variants even when route schemas are absent. Text bindings expose inline/file alternatives and stdin support; the displayed operation follows the selected execution variant. Generic `do` help keeps route parameters separate from shortcut-only options and includes its route execution plan's multipart/file, download, and WebSocket controls without duplicating path parameters. Authentication mechanics and generic transport flags stay local bootstrap behavior; product explanation, the recommended next steps, and the product command surface belong to the Worker so API changes do not require a CLI release just to discover or execute new operations.

The binary does not hardcode which action a bare `craken <resource>` runs. When no action is given, the CLI leaves the action empty and resolves it from the catalog shortcut's `defaultAction` field (for example the `workspace` shortcut advertises `list`), falling back to `help` when a resource declares no default. Resolver failures name the field that failed to resolve, so a command that resolves several ids reports which one was unknown.

Message page commands pass cursor options and `--limit` through to the Worker so service-side validation, clamping, and cursor semantics remain the source of truth.

Catalog commands can advertise table output plans. `--compact` emits those server-described columns as tab-separated rows for shell loops, while `--fields` keeps JSON output but projects only the requested dotted paths so scripts can omit large fields such as profile pictures without changing the service response contract.

The profile file is intentionally compatible with the prior Node CLI:

```text
${CRAKEN_CONFIG_DIR:-~/.config/craken}/config.json
```

Each profile stores `baseUrl` and `token`. `CRAKEN_PROFILE`, `CRAKEN_TOKEN`, and `CRAKEN_BASE_URL` provide the same environment overrides as the Node CLI.

`auth login` starts a server-side device login through `/api/client/device-authorizations`, prints the short code and verification URL, and polls `/api/client/device-token` until the browser approves the code. The CLI never opens a loopback callback listener, so the same command works from local shells, SSH sessions, and containers.

Realtime subscriptions use the WebSocket protocols advertised by the catalog command plan. `channel wait` is the channel-scoped alternative for agent loops that need one bounded long-poll response instead of the full workspace stream.

`auth login --as-agent` starts the external-agent variant through `/api/client/agent-device-authorizations` and `/api/client/agent-device-token`. The request includes a workspace id, agent name, client kind, optional client label, and optional scopes. The returned profile is still a bearer profile, but it also stores compatible metadata such as `kind: "agent"`, `agentId`, `agentName`, `clientKind`, and `workspaceId` so users can distinguish multiple agent roles on one machine.

Catalog WebSocket plans can advertise an additive `stream` descriptor containing single/batch envelope paths, scan cursor paths, message field mappings, and message-query defaults. The binary uses that descriptor for NDJSON records and existing nested field projection; event names, sender classification, mentions, conversation selection, and visibility remain server-owned. Limits count emitted records in message mode. Scan checkpoints advance only after successful output, and a partial batch never advances past its unconsumed tail.

Stream recovery uses the catalog's resume query and readable bootstrap operation/cursor path. The first listener run snapshots the current head before connecting, eliminating a read/connect gap through replay. Machine-local atomic checkpoints are scoped by server, profile, effective identity, expanded path/workspace, selection, and output shape; they contain only a version, scope hash, and activity cursor. Persistence follows successful output; partial batches checkpoint only consumed records. Bounded reconnect treats server authorization/protocol failures and output/checkpoint/data failures as terminal. Context cancellation interrupts dialing, reading, and retry timers; the executable propagates SIGINT/SIGTERM with conventional exit statuses. Product selection and DM replay visibility remain in the service.

Catalog execution now has a small local prepare boundary. It validates output options and the selected execution enums before resolver/file preparation, reparses server-declared boolean flags, and rejects unrecognized convenience options when a wire contract or explicit binding set is present. Raw argv and repeated values are retained; repeated scalars are rejected, while `--header` and `--query` preserve every occurrence. `--` ends option parsing.

`specification.wire` owns HTTP input locations and primitive types. Unbound complex/nullable/union convenience inputs require explicit JSON values; explicit string/text bindings preserve literal text and JSON bindings are decoded once. A complete `--json` body bypasses schema-shape validation and conflicts with body convenience options. Missing, false, explicit null and the string `"null"` retain separate meanings. The CLI performs no domain normalization or full JSON Schema validation. Legacy catalogs keep their existing fallback.

`do OP --help --format json` returns the original selected route and related commands, preserving unknown metadata, plus the selected execution plan. Local output format is separate from server Accept negotiation. Explicit headers override defaults; repeated `--header 'Name: value'` and `--query 'name=value'` provide raw HTTP input without product options. `--http-timeout 30s` controls transport timeout; JSON Content-Type can be explicitly supplied. Credentials use profiles/token flags rather than raw credential headers.

`--response-meta FILE` writes response status and headers as JSON independently of stdout body projection. Set-Cookie and credential headers are omitted. 201 Location, 202 acknowledgement, 204 no-body, 206 range and 304 not-modified retain their HTTP meaning. A 304 emits no body and preserves any download target; the CLI has no representation cache. Download bytes stream into a temporary sibling file before replacement.

`--error-format json` emits a CLI diagnostic envelope to stderr with stage (`prepare`, `request`, `response`, `decode`, `output`, or `local-persist`) and known HTTP evidence. Request failures without a response leave effect occurrence unknown. HTTP failures preserve server bodies (including Problem Details extensions), request IDs and Retry-After; credential-valued fields are redacted. Output and profile/metadata persistence failures after a response retain its status. No automatic mutation retries or new exit codes are introduced.

Resolvers bypass a lookup only for IDs matching the server's explicit `idPattern`; other names still use scoped collection lookup with ambiguity rejection. Within an invocation, resolver GET responses are shared by expanded URI. Bearer credentials stay on the configured origin, including redirect handling.

The focused `testdata/server-catalog.json` fixture comes from Craken Agents' `bin/export-client-catalog.mjs`, rather than a manually recreated API. Refresh it after server contract changes and run the hermetic CLI boundary tests; production endpoints are unnecessary.
